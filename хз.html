Мини-памятка: Issue и Pull Request в GitHub

Часть 1: Issue — это не просто «проблема»

В GitHub Issue — это универсальный инструмент для отслеживания задач, обсуждений и ошибок. Это не обязательно «баг»; это может быть запрос функции, вопрос или заметка о необходимости доработки.

Ключевые компоненты Issue:

  • Title (Заголовок): Краткое и ёмкое описание сути.
  • Description (Описание): Подробности. Здесь можно использовать Markdown для форматирования, прикреплять скриншоты и ссылки.
  • Assignees (Исполнители): Кто отвечает за решение.
  • Labels (Метки): Категории (например, bug, enhancement, documentation, good first issue). Помогают фильтровать задачи.
  • Milestone (Веха): Привязка к конкретному сроку или версии проекта.
  • Projects (Проекты): Канбан-доски для визуализации прогресса.

Зачем это нужно? Issue создаёт «единицу работы». Когда вы начинаете что-то делать, лучше сначала создать Issue (или взять существующий), чтобы все видели, что задача в работе, и не дублировали усилия.

Часть 2: Pull Request (PR) — предложение изменений

Pull Request — это запрос на слияние ваших изменений из одной ветки в другую (обычно в main). Это механизм Code Review и обсуждения кода перед тем, как он попадёт в основную кодовую базу.

🔄 Полный цикл работы с PR (Workflow)

Шаг 1: Подготовка ветки
Не работайте напрямую в main. Создайте отдельную ветку под конкретную задачу.

Шаг 2: Коммиты
Делайте коммиты небольшими и осмысленными. Сообщение коммита должно объяснять что и зачем сделано.

Шаг 3: Создание PR
На GitHub появится кнопка «Compare & pull request». Нажмите её.

  • Base (Куда): Ветка, в которую вы хотите влить изменения (обычно main).
  • Compare (Откуда): Ваша ветка с изменениями.

Шаг 4: Заполнение описания
Это критически важно. Хорошее описание PR должно содержать:

  • Что сделано: Краткое резюме.
  • Зачем: Ссылка на Issue, который это решает.
  • Как проверить: Шаги для тестирования (если применимо).
  • Скриншоты: Если изменения визуальные.

Шаг 5: Review и Merge
Ревьюер оставляет комментарии. Вы можете вносить правки в той же ветке и пушить — они автоматически добавятся в PR. После одобрения (Approve) нажимается Merge.

Часть 3: Магия связывания Issue и PR (Keywords)

Это самый важный лайфхак. Вы можете автоматически закрыть Issue, когда PR будет смержен, используя специальные ключевые слова в описании PR или в сообщении коммита .

Синтаксис:

  • Closes #10 (если Issue в том же репозитории)
  • Fixes owner/repo#100 (если Issue в другом репозитории)
  • Resolves #10, resolves #123 (для нескольких задач)

Важное ограничение: Ключевые слова срабатывают только если PR нацелен на ветку по умолчанию (обычно main). Если вы льёте в другую ветку, автоматического закрытия не произойдёт .

Другие полезные ключевые слова: close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved. Регистр не важен, двоеточие опционально (Closes: #10 тоже работает) .

Часть 4: Продвинутые фишки

  • Draft PR (Черновик): Если работа ещё не готова к ревью, но вы хотите показать прогресс или получить ранний фидбек, создайте Draft PR. Его нельзя смержить, пока вы не нажмёте «Ready for review» .
  • Squash and Merge: Позволяет объединить все коммиты из вашей ветки в один коммит в main. Это делает историю чище, особенно если у вас было много мелких коммитов типа «fix typo» .

🎯 5 задач для отработки

Ниже — практические сценарии. Выполняйте их в своём тестовом репозитории (можно создать пустой репозиторий на GitHub).

Задача 1: Базовый цикл (Issue → PR → Merge)

  1. Создайте в своём репозитории Issue с заголовком «Добавить файл README».
  2. В описании Issue напишите: «Нужно создать README.md с описанием проекта».
  3. Создайте ветку feature/add-readme, добавьте файл README.md с любым текстом.
  4. Запушьте ветку и создайте Pull Request.
  5. В описании PR напишите: Closes #1 (где 1 — номер вашего Issue).
  6. Смержите PR. Убедитесь, что Issue автоматически закрылся.

Задача 2: Связывание через коммит

  1. Создайте новый Issue: «Исправить опечатку в README».
  2. Создайте ветку, исправьте опечатку в README.
  3. Сделайте коммит с сообщением: Fix typo in README (fixes #2).
  4. Запушьте и создайте PR (описание можно оставить пустым).
  5. Смержите PR. Проверьте, закрылся ли Issue #2 автоматически.

Задача 3: Разрешение конфликта (Симуляция)

  1. В своём репозитории создайте файл conflict.txt с текстом Строка A в ветке main.
  2. Создайте ветку feature/change-a, измените текст на Строка B, закоммитьте, но не мержите.
  3. Вернитесь в main, измените тот же файл на Строка C, закоммитьте.
  4. Теперь создайте PR из feature/change-a в main. GitHub покажет конфликт.
  5. Локально в ветке feature/change-a выполните , разрешите конфликт вручную (оставьте нужный текст), сделайте добавление и rebase .
  6. Запушьте ветку и завершите PR.
